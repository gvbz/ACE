# Virindi compatibility review

## Known-gap audit and interaction follow-up (2026-11-13)

This is the current UCM comparison summary. Older dated sections below preserve
investigation history; their remaining-gap lists are not current task lists.
The audit distinguishes defects in implemented behavior from features that still
need a separate implementation or external data.

Gap-register implementation closure (2026-11-13):

- **Conditional and balancing regex groups are implemented.** Imported loot
  rules, meta expressions and Lua `regextest`/`regexmatch` use capture participation
  for conditional branches and capture stacks for balancing groups. Backtracking
  restores captures that a failed branch removed; repeated names share a stack,
  and balancing underflow fails the branch. Assertion conditions, atomic groups,
  lookbehind, greedy/lazy repetition and mixed named/numeric references compose
  with these constructs. Ordinary patterns retain the ICU fast path.
- Pattern, text and capture-name keys preserve case. This also fixes an existing
  predicate-cache defect where a result for one capitalization could be reused
  for another. Lua receives distinct case-sensitive capture keys directly rather
  than through a case-folding JSON object.
- Work limits remain deliberate: 2 ms per match, 64 KiB of backtracking storage,
  32 captures, 2,048 pattern characters and 4,096 input characters. The history
  engine also bounds capture storage, repetition constructs, nesting and total
  instructions. Limit failures remain errors, never cached ordinary nonmatches.
  See [Lua helper limits](PublicAPI.md#sandbox-helper-functions).
- This closes the last recorded **in-scope native implementation** gap. External
  integrations remain excluded by the user's instruction. Server-specific recipe
  data and actual live-server/device acceptance are separate requirements below;
  implementation closure does not mark those checks as performed.

The regex fixtures are generated by the installed .NET engine, with both match
results and final captures recorded. The generator and 2,790 cases live in
`Source/ACEClient/Private/Tests/Fixtures/Generate-VTRegexOracle.ps1` and
`VTRegexDotNet.json`. The suite also checks invalid imports, bounded pathological
patterns, repeated calls after a limit error, cache case sensitivity and Lua
capture delivery. A real imported meta lookup selects a balanced matching object
instead of a closer unbalanced name. Semantics are cross-checked with Microsoft's
[conditional constructs](https://learn.microsoft.com/en-us/dotnet/standard/base-types/alternation-constructs-in-regular-expressions)
and [balancing groups](https://learn.microsoft.com/en-us/dotnet/standard/base-types/grouping-constructs-in-regular-expressions).
The same 2,790 fixtures agree between installed .NET 10.0.14 and .NET Framework
4.8.10008.0 (the runtime family used by vTank).

Native combat and regex follow-up (2026-11-13):

- **Physical proc debuffs** now participate alongside learned spells, wand
  activation and grenades. As in VT `ga.cs`/`dz.cs`, the first assessed spell must
  be an offensive timed non-War/non-Item debuff. UCM compares its power and item
  spellcraft, equips the weapon and any matching ammunition, and uses ordinary
  melee attacks at minimum power or missile attacks at full accuracy. It never
  sends the proc as a learned cast or pretends an attack guarantees a proc.
  Confirmation, target loss, rejection or a ten-second deadline ends the attempt;
  repeat attacks are cancelled. Melee approach respects the existing range and
  navigation settings. Native dispatch rechecks source, hand, mode and activation.
- **Offhand selection** also applies to thrown main-hand weapons, matching VT's
  `fi.h` branch. Damage-modifier and slayer multipliers are now included in the
  offhand tie-break, consistently with the main hand. VT's slayer/rend/confirmed
  vulnerability/bonus ordering remains primary; displayed damage never overrides
  a required element. Shield preference and explicit/tether assignments remain.
- **Regex** now supports global/scoped `x` (whitespace/comments) and `n` (explicit
  captures), including disabling them inside groups. Numbered backreferences are
  translated from .NET's unnamed-first numbering, even when named groups appear
  first; numeric `\k<1>`/`\k'1'` forms and missing-group octal fallback are handled.
  Token boundaries are preserved: whitespace cannot repair invalid group names
  or turn literal spaced braces into quantifiers. These semantics were checked
  against the local .NET implementation and Microsoft's
  [grouping](https://learn.microsoft.com/en-us/dotnet/standard/base-types/grouping-constructs-in-regular-expressions)
  and [option rules](https://learn.microsoft.com/en-us/dotnet/standard/base-types/regular-expression-options).
- External integration work is excluded following the user's explicit instruction.
  The subsequent closure above implements the remaining native regex work;
  live acceptance is still tracked separately.

Additional source-verifiable gaps implemented (2026-11-13):

- **Debuff selection** compares learned spells, assessed innate wand spells and
  registered grenades by spell strength or casting skill, with learned spells
  winning equal scores. Item spellcraft is separate from the player's school
  skill. Grenades import `GrenadeOptions` from the adjacent `gameinfodb.ugd`;
  type 7 assist items require valid data and rechecked wield requirements. Actual
  debuff confirmation, not a successful use receipt, ends the attempt. Grenade
  repeat attacks are cancelled on result, target loss or timeout.
- **Idle helper buffs** are optional and off by default. Eligible nearby players
  within 18 metres and clear sight receive a random learned protection/helper
  family at the configured minimum interval. This is idle work and makes no
  claim to know another player's existing buffs. Source: `ba.cs` and the
  [official helper FAQ](https://www.virindi.net/wiki/index.php/Virindi_Plugins_FAQ).
- **Optional casting movement** imports `DoJiggle` and `JumpOutWandCasting` and
  exposes both controls in UCM. They default off, leaving normal freer casting
  unchanged. Jiggle uses backward/alternating strafe input; the item-cast jump
  is a bounded request. Manual input, UI blocking, stop, session changes and
  completion cancel these controls. Sources: `e5.cs`, `gj.cs`, `gs.cs` and the
  [official advanced options](https://www.virindi.net/wiki/index.php/Virindi_Tank_Advanced_Options).
  Real-server animation timing still needs acceptance; the client never bypasses
  collision or predicts that the server accepted a spell.
- **Custom server crafting** can import a validated JSON catalog through Auto
  Craft, shared with UCM. Catalogs merge over bundled recipes, persist separately
  for each server, reject invalid replacements atomically and cannot change
  during a crafting job. See [recipe catalog format](PublicAPI.md#server-crafting-catalogs).
- **Classic expression metadata** no longer incorrectly blocks rule import.
  Decompiled `VTClassic/cLootItemRule.Match` and `EarlyMatch` evaluate the normal
  requirements only; `CustomExpression` is read/written but never evaluated.
  UCM retains that field for round trips and uses the same requirement semantics.
- **Regex compatibility** adds bounded lookbehind, comment groups and both named
  backreference spellings, retaining .NET capture numbering and all work limits.
- The full-spellbook test caught extra allocation/lookup work in the debuff
  selector. Learned candidates now reuse immutable spell rows and the preference
  is resolved once per decision; no sandbox budget was increased.

Automatic fellowship and integrated crafting follow-up (2026-11-13):

- **Buff others → Automatic fellowship management** is off by default. It
  implements VT `bf.cs` / `g5.cs` tell recruitment (`xp`), queue queries
  (`line`, `list`, `status`), `remove`, `leader`, member-only `location` and
  `help`. The leader closes recruitment while reserving FIFO waiting-list
  spots for five minutes. A reserved player must return within 10 metres and
  send `xp` again. Leadership changes clear reservations, votes and bans.
  Capacity defaults to retail's nine but is configurable for custom servers.
- Optional member votes support `startvote kick/ban/giveleader NAME` and
  `startvote setopen true/false`, with `vote ID yes/no`. As in VT, voting lasts
  two minutes, requires a strict majority of votes cast (no quorum), ignores
  departed voters and limits proposal starters to once per four minutes.
  The local leader can use `/ucm fellow vote ID yes/no/abort`,
  `/ucm fellow clear`, and `/ucm fellow unban NAME`. Commands are rate limited;
  queues and concurrent votes are bounded. Private manager tells stay in UCM.
- **Recovery → Automatic crafting** integrates the existing recipe catalog and
  executor with UCM. VT `a9.cs` / `uTank2/cLogic.cs` replenish assist supplies and
  buff items in critical, normal and idle phases. UCM imports `AutoCraftItems`
  and all six `IdleCraftCount_*` targets, and also supports an explicit named
  supply list with stock minima. It manufactures ammunition and ordinary
  supplies from available recipe ingredients; intermediate ingredients can be
  crafted recursively. It does not invent recipes for unknown custom items.
- UCM crafts one output batch at a time, checks fresh stock before dispatch,
  excludes retained/equipped/traded inputs and nonempty containers, respects
  trained crafting skills, enters peace and uses the existing split/merge and
  confirmation handling. Inventory changes confirm results; unrelated errors
  cannot finish a craft. Emergency recovery wins between crafting actions;
  failures pause only crafting, leaving navigation and other activities active.
  A failed or uncertain supply is excluded until UCM restarts or automatic
  crafting is toggled; trying another recipe for it cannot create a retry loop.
- `AutoFellowManagement` and `AutoCraftItems` now import into executable policies
  and can be changed by VT meta setting commands. Both native enable switches
  stay local to the UCM setup; their configuration stays in Character profiles.
  Native defaults are off. VT imports use the verified bundled defaults from
  `uTank2.Resources.defaultsettings.usd`: both enabled, two idle kits and fifteen
  idle food items per configured type unless explicitly overridden.
- ACE/GDLE use the same existing validated fellowship, UseWithTarget and
  inventory-result paths. Requests never predict membership or crafting output.
  Unlike VT's repeated recruitment attempts, UCM submits one invitation and
  waits up to 30 seconds for membership, then asks the applicant to try again.
  Supported catalog recipes, actual server permissions and received player
  state remain requirements. These are local regression fixtures, not a live
  ACE/GDLE soak test.

## Ordinary route interactions and scheduler priority (2026-11-10)

VT `uTank2/cLogic.cs::InitializeDefaultLogicRules` schedules normal recharge before
navigation; `g8.cs` and `cr.cs` honor navigation/item-use locks independently.
The existing portal/recall handling in UCM yielded after the native action gate
cleared, but an ordinary Use waypoint returned before recovery or combat could
run. Ordinary Use now yields in the same way without resubmitting the item.

Navigation advances only on a completed use for its recorded item, with a newer
action serial and a request timestamp from that waypoint attempt. Healing-item
receipts, unrelated failures and older uses of the same item cannot complete or

Portal/recall arrival still requires teleport/position evidence. Legacy snapshots
without correlated history retain their previous action-counter fallback.

This closes the ordinary route-use wait gap from the previous pass. Meta-command
interaction waits, exact recovery-efficiency heuristics, and the other incomplete
features listed below remain separate work; this is not a complete VT port.

## Recovery priority and streak finishing (2026-11-09)

This pass compared the supplied VT `cr.cs` recharge scheduler, `hi.cs` combat
selector and `es.cs` target-health tracker with the current UCM script.
The older dated lists below are historical evidence, not a current feature list.

- VT checks health before stamina before mana once its item-use lock permits.
  UCM now tracks pending recovery separately per vital. A mana/stamina receipt
  wait no longer postpones a needed heal after the native action gate is free.
  Completion identity, request time and effect confirmation prevent a late mana
  failure or an unrelated use result from completing/rejecting an in-flight heal.
  Unconfirmed uses are not resubmitted; vital replication still confirms effects,
  and timeouts retain the existing bounded fallback behavior.
- In mixed bolt/streak mode, VT chooses a streak only at positive remaining HP
  below integer `(last single-target spell damage, or streak Difficulty)/7`.
  UCM now follows that finishing rule using target-specific health and confirmed
  spell damage, instead of comparing spell power alone. New health samples replace
  old estimates, duplicate hits are ignored, and different targets do not share
  damage estimates. Streak-only mode remains unconditional when usable; missing
  streak/ring spells can fall back to bolts/arcs. Available rings keep priority.

Rechecked gaps: vendor restocking, mana-stone donor looting/refilling, Classic's
standard palette/color rules, and optional ghost-target suppression already have
runtime implementations and regression coverage. They are not open gaps simply
because older entries below list them. Automatic fellowship management, DoJiggle,
random helper buffs, general crafting/ammunition manufacture, complete non-fellow
assistance, custom loot expressions/User actions, and external plugin/multi-client
integrations remain incomplete. Unsupported enabled imports remain explicit errors.
Ordinary route/meta use waits and the exact recovery-efficiency heuristics still

## ILT custom wand property-dump follow-up (2026-11-04)

The later UB appraisal for Blunt Sceptre (WCID 29260, GUID F06A016A) identifies
the remaining blocker: requirement type 13 in slots 3/4, referencing 64-bit
character properties 9007 >= 5500 and 9009 >= 3500. ILT defines type 13 as
Int64Stat and performs a minimum comparison against PropertyInt64. Its Creature
and Life augmentation counters are not marked SendOnLogin, so their absence
from client data cannot be treated as a confirmed zero. The description also
mentions an Item requirement, but the raw dump does not contain that triplet;
the client does not invent requirements by parsing description prose.

Sources pinned to ACECustom commit 718dc8b3033d66a2e816aee27c8c470002597b28:

- [WieldRequirement enum](https://github.com/rkroska/ACECustom/blob/718dc8b3033d66a2e816aee27c8c470002597b28/Source/ACE.Entity/Enum/WieldRequirement.cs)
- [Server wield checks](https://github.com/rkroska/ACECustom/blob/718dc8b3033d66a2e816aee27c8c470002597b28/Source/ACE.Server/WorldObjects/Player_Inventory.cs)
- [Int64 properties and replication attributes](https://github.com/rkroska/ACECustom/blob/718dc8b3033d66a2e816aee27c8c470002597b28/Source/ACE.Entity/Enum/Properties/PropertyInt64.cs)

UCM now checks reported Int64 counts without truncation and defers unreported
counts to the normal server-validated equip request. This follows the supplied
VT ga.cs requirement helper's behavior of permitting server validation for
requirements beyond its local checks. Known unmet requirements still block;
unsupported kinds still produce an explicit diagnostic. The equipment pool and
Lua snapshot distinguish deferred validation from known eligibility. Server
confirmation and the existing bounded equip retries remain authoritative.

Only Int64 properties referenced by carried equipment invalidate cached item
rows. Presence is part of the cache key, so receiving zero replaces an unknown
count; ordinary XP/luminance updates do not rebuild every inventory entry.
Fixtures use the dump's actual requirement, element, rend, slayer and caster
bonus properties, with separate synthetic character counts. They exercise native
snapshots, real private Int64 packets, automatic/pool/explicit selection and the
shipped Lua casting policy. Live ILT acceptance remains a player verification.

Win64 Development editor build passed. CustomWieldRequirements,
VTankWeaponSelection, EquipmentBuffCycle, ActivityFailureIsolation,
ImportAndSettingsUI and UCMIdleWorkload passed with zero test errors or warnings.
Evidence: `TestOutput/UCMInt64Wands-20261104/report/index.json` and `tests.log`.

## Mob controls and recovery follow-up (2026-11-04)

The matrix now includes numeric priority (P, -1 through 10) and a Remove action
on each non-default row. Pet selection remains in Details alongside weapon and
offhand selection. Native rows copy Default when created and retain their own
values; opening an older inherited row materializes its current settings before
Default can be edited. Copy Default settings is an explicit action. Native name
matching uses the longest matching prefix, with exact matches winning ties;
imported VT expression rules retain their first-match order.

Ordinary attacks (A) no longer gate debuff-only target admission. Bolt/arc

## Navigation

Walking, pauses, portal GUIDs, named world objects, recall spells, commands,
checkpoints and directional jumps use normal client actions and movement.
Circular routes wrap; Linear routes reverse; Once routes stop at the end. Position
conversion preserves VT coordinate units, negative dungeon-local coordinates and
height. Indoor NAV coordinates resolve in the current dungeon block. Portals and
recalls wait for a server teleport sequence and the end of portal space, including
at the final waypoint. Checkpoints also wait for the server position.

Follow routes can retain the other player's observed path around corners.
The path is bounded to 512 observations and resets after teleport/disappearance;
it is not an obstacle-solving pathfinder. Doors can be opened on the active
walking segment. Navigation priority, distance, idle peace and main-pack cramming
are supported options. Movement never writes a pawn position or bypasses collision.
The route overlay updates for embedded and loaded routes. NAV has no indoor cell
IDs, so conversion alone cannot establish that a dungeon route is traversable.
Host movement uses the profile's waypoint tolerance, including imported
NavCloseStopRange. It no longer stops at a fixed 70 cm when the route requires a
closer arrival. An unreachable waypoint height retains the progress watchdog.

## Buffs, combat and recovery

Automatic self buffing includes usable innate skills, as well as trained skills.
Creature, life and equipment-compatible item buff families are confirmed before
advancing; item auras target the player rather than every carried item. Buff-other
requests have bounded confirmation waits and report unconfirmed families instead
of treating them as successful. The host also stops on a lost cast acknowledgement.

Self-buff order was verified against VT `eq.cs` (`BuffController`), whose
`b()` builds Creature Enchantment Mastery, Focus, Willpower, Mana Conversion
and Life Magic Mastery first; its cast selector consumes that list in order.
UCM uses those family priorities for normal and forced cycles, followed by the
other trained magic schools. Server-reported current skills determine the next
usable tier; no predicted skill gains are substituted for network updates.

Recovery ordering was checked against VT `m.cs` / `he.cs`: Regular Spell uses
Heal Self, Revitalize Self and Stamina to Mana. UCM keeps direct Mana Boost as a
fallback. VT `gj.cs` returns its cast state to idle on a matching completion;
UCM now releases its fixed request delay on server UseDone, retaining busy and
pending-action checks. UCM's automatic maintenance deliberately excludes buffs
under five minutes; explicitly selected short buffs remain supported with a
bounded renewal window. DAT-backed regressions cover Tusker Leap (10 seconds),
regular Jump VIII, conversion followed by Revitalize, and mana-boost fallback.

Weapon/spell choices use known requirements and resistance data. A launcher's
elemental override is evaluated against its ammunition, not the bow's intrinsic
piercing damage type. Unknown compatible ammunition is appraised; unavailable
loadouts stop instead of attacking with previously equipped, incompatible ammo.
Healing kits require trained Healing and remaining uses, allowing another
consumable or recovery spell when a carried kit cannot be used.

## Meta programs and commands

The bounded interpreter supports ordered once-per-state rules, compound actions,
All/Any/Not, calls/returns, embedded routes, ordinary state timers, movement
watchdogs, chat captures, monster/range conditions, inventory counts, pack space,
level/burden, vendor state, death recovery, buff-needed checks, enchantment time,
portal events and distance from navigation points.

Expressions support variables, stopwatches, arithmetic/comparison/Boolean
operators, sequencing, regex comparison, quoted/escaped strings, world lookup,
object names/coordinates, player coordinates, distance, string conversion and
try-use/try-apply actions. String comparisons are case-insensitive. Boolean
operands are eager and &&/|| have equal precedence, as in the reference evaluator.
Supported VT option get/set actions convert map distances to/from meters.

Native command adapters include named use/apply/select/give, inventory-only and
world-only searches, combat mode, facing, jumps, recall aliases, fellowship
creation/recruiting/openness/quit, logout, local/fellowship chat, force buffing,
visible echo notices, server-confirmation responses and supported VT options.
Commands are parsed into constrained intents; no imported command executes an
OS shell or arbitrary client command. Exact names precede partial-name matches.
Confirmation responses require the `confirm` capability and the exact currently
pending server type/context; they do not click arbitrary screen coordinates.
Existing installations must re-enable UCM to grant added capabilities.

Literal profile loads resolve same-folder dependencies case-insensitively,
including cyclic meta references, before activation. Limits are 64 files,
4 MiB per source and 8 MiB aggregate source. Missing/unsupported dependencies
block the whole import. Dynamic profile names only load files already validated
in that library. Loading a route clears the old pending route; loading a loot
profile replaces its salvage policy. Nothing starts automatically at login.

## Loot classification and actions

First matching rule wins; an unsupported earlier Skip rule cannot fall through to
Keep. Decal classes derive from server item categories and flags. Supported
requirements cover integer/decimal/string properties, spell names/counts, exact
palettes, material/workmanship/value, skill/level/free slots, minimum damage,
buffed melee/missile/property values, potential tinkered damage/defense/offense
and combined ratings. Missing properties use the imported rule's zero semantics.
Appraisal precedes decisions that require data not yet known.

Weapon-skill rules retain VT's distinct integer properties: `EquipSkill`
(`218103840`) comes from the weapon appraisal profile's `weapSkill`, while
`WieldReqAttribute` (`159`) comes from item integer qualities. Verified against
the supplied `utank2_decompiled/g6.cs` appraisal handler,
`uTank2/LootPlugins/IntValueKey.cs`, `GameItemInfo.GetValueInt`, and Virindi's
[Weapon Skill Ids reference](https://www.virindi.net/wiki/index.php/Weapon_Skill_Ids).
The builder offers named IDs for Creature 31, Finesse 46, Heavy 44, Item 32,
Life 33, Light 45, Mana Conversion 16, Missile 47, Summoning 54, Two-Handed 41,
Void 43, and War 34, plus custom numeric IDs. These remain ordinary integer
conditions; the picker does not substitute properties or infer an item skill
from its name. Raw `WeaponSkill` (`48`) remains independently editable.
`ACE.Plugins.WeaponSkillLoot` exercises the actual picker, saved profile reload,
VT UTL conversion, native appraisal snapshots and shipped UCM loot decisions,
including distinct attack/wield skills, unknown appraisal data and custom IDs.

Regex matching uses ICU with .NET capture numbering and both named-capture
spellings. It is case-sensitive unless the pattern specifies otherwise; VT's
expression regex operator supplies its required case-insensitive flag. Patterns
are limited to 2,048 characters, 32 capture groups, 4,096-character input,
2 ms match time and 64 KiB regex stack. Aggregate regex work is bounded per tick.
Bounded lookbehind, `(?#comments)` and both named-backreference spellings are
supported. Conditional/balancing groups, extended mode (`x`), unbounded
lookbehind and numeric backreferences mixed with named captures remain
unsupported, with explicit import errors.

Keep/Skip/KeepUpTo, Salvage, Sell and Read work through normal inventory actions.
Only items transferred by UCM's current loot session are queued for destructive
post-loot actions. Split stacks resolve their new server GUID. Changed, equipped,
retained or traded possessions cannot be silently substituted. Ambiguous merges
stop for review. Sales wait for an open vendor. Server errors and action timeouts
stop instead of repeatedly selling or destroying items. Pending post-loot jobs
are session-local and do not survive Stop/logout.
Final-item ownership confirmation and post-loot actions survive a corpse closing
automatically. A recently auto-closed corpse is temporarily suppressed while its
world removal catches up. Imported KeepUpTo rules count exact item names across
WCIDs, as VT's `hv` / `f9.a` inventory counting does; native rules retain WCID scope.

SalvageCombine workmanship groups, material overrides and value thresholds import
from UTL. Combining is a separate opt-in control. The loot editor exposes those
groups and thresholds as well as calculated/character conditions, rule order,
actions and property filters. Matching partial bags combine only with the same
material; requests wait for removal of their source GUIDs. The editor and runtime
validate ranges, ownership and request bounds. Rule files retain unsupported
source data for round-trip export; saving an editable source is not activation.
